# AI Engineering 요약 (칩 후옌)

> 10개 챕터의 핵심을 한 파일에 정리한 것.  
> 책 전체를 관통하는 메시지: **모델보다 평가와 데이터가 핵심이고, 복잡한 것부터 시작하지 말고 단순한 것부터 검증하라.**

## 1장. 파운데이션 모델을 활용한 AI 애플리케이션 입문

- 언어 모델은 자기 지도 학습 덕분에 레이블 없이 대규모 데이터로 학습 가능 → LLM 확장의 핵심
- AI 엔지니어링 = 모델을 만드는 것이 아니라 **이미 있는 모델로 애플리케이션을 만드는 것**
- 모델 조정 복잡도 순서: 프롬프팅 → RAG → 파인튜닝
- 경쟁 우위 3요소: 기술력 · 유통력 · 데이터 → 스타트업이 확보 가능한 건 **데이터**

## 2장. 파운데이션 모델 이해하기

- 모델의 능력과 한계는 **학습 데이터**가 결정한다
- 트랜스포머의 어텐션 메커니즘이 seq2seq의 병목을 해결했지만, 자기회귀 디코딩의 순차 생성 문제는 여전히 남아 있음
- 사후 학습(RLHF): "다음 토큰 예측" → "사람이 원하는 응답 생성"으로 모델을 전환하는 과정
- 온도 · top-k · top-p 같은 샘플링 전략 = AI의 비일관성과 환각의 근본 원인이기도 함

## 3장. 평가 방법론

- AI가 강력해질수록 평가는 더 어려워진다
- 개방형 출력은 정답이 하나가 아니어서 전통적인 평가 방식이 통하지 않음
- 평가 방법 발전 순서: 기능적 정확성 → 어휘적 유사도(BLEU/ROUGE) → 의미적 유사도(BERTScore) → AI 평가자
- AI 평가자의 한계: 자기 편향 · 장황성 편향 · 비일관성

## 4장. AI 시스템 평가하기

- 목표: 좋은 모델이 아니라 **우리 애플리케이션에 맞는 모델** 고르기
- 평가 기준: 도메인 능력 · 생성 품질 · 지시 수행 능력 · 비용 · 지연 시간
- 공개 벤치마크 = 나쁜 모델을 거르는 용도, 결국 **자체 평가 파이프라인**이 필요
- 평가 파이프라인은 비즈니스 지표와 연결되어야 의미가 있음

## 5장. 프롬프트 엔지니어링

- 프롬프팅 = 체계적인 실험이 필요한 ML 작업, 별것 아닌 게 아님
- 성능을 높이는 기법: 퓨샷 예시 제공 · CoT(단계별 사고) · 자기 비판
- 모델은 프롬프트 **중간보다 시작과 끝**을 더 잘 기억함 (NIAH 테스트)
- 방어적 프롬프팅으로 탈옥 · 프롬프트 주입 등의 공격에 대비해야 함

## 6장. RAG와 에이전트

- RAG = 각 질의에 맞는 컨텍스트를 외부에서 동적으로 가져오는 기술, 환각 감소에 효과적
- 검색 방식: 키워드 기반(TF-IDF, BM25) + 임베딩 기반(벡터 검색) → 하이브리드 검색이 일반적
- 에이전트는 도구를 통해 현실 세계와 상호작용, ReAct 패턴(추론→행동→관찰 반복)이 표준
- 메모리 3계층: 내부 지식(모델 가중치) · 단기(컨텍스트) · 장기(외부 DB)

## 7장. 파인튜닝

- 파인튜닝에는 데이터 · 하드웨어 · ML 지식이 필요 → **가장 먼저 시도할 방법이 아님**
- 선택 기준: **RAG은 사실을 위한 것, 파인튜닝은 형식을 위한 것**
- PEFT 기법 중 LoRA가 현재 가장 널리 쓰이고, QLoRA로 메모리 사용량을 대폭 줄일 수 있음
- 모델 병합: GPU 없이 여러 파인튜닝 모델의 장점을 결합하는 방법

## 8장. 데이터셋 엔지니어링

- 모델이 대중화될수록 차별점은 결국 **데이터**
- 좋은 데이터의 조건: 관련성 · 일관성 · 고유성 · 충분한 커버리지
- AI 합성 데이터는 유용하지만, 반복 학습 시 모델 붕괴(model collapse) 위험 → 실제 데이터와 혼합 필요
- 가장 좋은 데이터 소스 = 자체 애플리케이션의 실사용 데이터

## 9장. 추론 최적화

- LLM 추론의 두 병목: 프리필(연산 제약) vs 디코딩(메모리 대역폭 제약)
- 모델 수준 최적화: 양자화 · 증류 · 프루닝
- 알고리즘 수준 최적화: 추측 디코딩 · KV 캐시
- 서비스 수준 최적화: 연속 배치 처리(continuous batching) · 프리필·디코딩 분리 · 프롬프트 캐싱

## 10장. AI 엔지니어링 아키텍처와 사용자 피드백

- 권장 아키텍처 구성 순서: 질의→응답 → 컨텍스트 보강 → 가드레일 → 라우터/게이트웨이 → 캐싱 → 에이전트 패턴
- 관찰 가능성(모니터링 · 로그 · 트레이스)은 설계 초기부터 고려해야 함
- 암시적 피드백(조기 종료 · 오류 교정 · 재생성)이 명시적 피드백보다 훨씬 풍부하지만 해석이 어려움
- 피드백을 잘못 활용하면 **퇴화 피드백 루프** 발생 가능
