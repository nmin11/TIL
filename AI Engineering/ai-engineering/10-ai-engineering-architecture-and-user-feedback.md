# 10. AI 엔지니어링 아키텍처와 사용자 피드백

- 10장에서는 이전에 배운 다양한 기법들을 어떻게 조합해서 제품을 만들 수 있을지 살펴볼 것
- AI 엔지니어링 기법 및 도구는 다양하므로 적절한 것을 선택하기 쉽지 않음
- 성공적인 애플리케이션에는 결국 사용자 피드백이 필요

## 10.1 AI 엔지니어링 아키텍처

- 가장 단순한 아키텍처에서 시작해 점진적으로 더 많은 구성요소를 추가하는 방식으로 살펴볼 것
- 가장 단순한 형태의 모습
  - 애플리케이션이 질의를 받아 모델로 보내는 방식
  - 모델은 응답을 생성해서 사용자에게 반환
  - 컨텍스트 증강, 가드레일, 최적화 등이 없는 상태
- 단순한 형태에서 구성요소를 추가는 대략적인 과정
  - 외부 데이터 소스 및 도구 접근이 가능하도록 만들어서 컨텍스트 보강
  - 시스템 및 사용자 보호를 위한 가드레일 도입
  - 파이프라인을 도입하고, 보안 강화를 위해 모델 라우터 및 게이트웨이 추가
  - 캐싱을 통해 지연 시간 및 비용 최적화
  - 시스템 성능 극대화를 위해 로직 및 실행 기능 보강
- 이 책에서는 일반적인 방법을 소개하지만, 애플리케이션의 상황은 저마다 다르므로 모든 상황에 통용되지는 못할 것

### 1단계: 컨텍스트 보강

- 질의 응답에 필요한 컨텍스트를 시스템이 구축할 수 있도록 메커니즘 추가
- 컨텍스트는 텍스트 검색, 이지 검색, 표 형태 데이터 검색 등 다양한 검색 메커니즘을 통해 구성 가능
- API들을 활용해서 모델이 자동으로 정보를 수집하게 할 수도 있음
- **컨텍스트 구성(context construction)**
  - 파운데이션 모델을 위한 **특성 공학(feature engineering)** 과 같음
  - 모델이 출력을 생성하는 데 필요한 정보 제공
  - 시스템의 출력 품질에 핵심적인 역할 수행
  - 거의 모든 모델 API 제공업체가 이 기능을 지원
    - 다만 제공업체별로 컨텍스트 구성 지원 방식이 제각각

### 2단계: 가드레일 도입하기

**입력 가드레일**

- 보통 2가지 유형의 위험을 막아줌
  - 외부 API로 개인정보가 유출되는 위험
  - 시스템을 망가뜨릴 수 있는 악성 프롬프트가 실행되는 위험
- 서드파티 API를 사용할 때 잠재적 유출을 완벽하게 막을 순 없음
  - 하지만 가드레일을 통해 줄여나갈 수 있다
- 민감 데이터 자동 탐지 도구 활용
  - 어떤 데이터가 민감한 데이터인지 여부는 직접 정해야 함
  - 일반적인 민감 데이터 유형
    - 개인정보
    - 사람 얼굴
    - 회사 지적 재산 및 기밀 정보
  - AI를 사용해 잠재적 민감 정보를 식별
  - 민감 정보가 확인되었을 경우의 선택지들
    - 질의 전체 차단
    - 민감 정보만 제거

**출력 가드레일**

- 주요 기능 2가지
  - 출력 실패 탐지
  - 다양한 실패 유형을 처리하는 정책 명시
- 기준에 못 미치는 출력을 잡아내기 위해서는 실패가 어떤 모습인지 알아야 함
  - 모델이 응답해야 하는 상황에 빈 응답을 내놓는 경우 등
- 품질과 보안 중점의 실패 사례들
  - 품질
    - 예상 출력 형식을 따르지 않는 응답
    - 사실과 일치하지 않는 응답 (환각)
    - 전반적으로 수준 낮은 응답
  - 보안
    - 인종차별적이거나 성적인 콘텐츠 또는 불법적인 활동을 담은 유해한 응답
    - 개인정보나 민감한 정보가 포함된 응답
    - 원격 도구나 코드 실행을 유발하는 응답
    - 자사나 경쟁사에 대해 잘못 설명해서 브랜드에 위험을 초래하는 응답
- 보안 측정 시에는 **오거부율 지표(false refusal rate)** 확인도 중요
  - 과한 보안은 사용자의 작업을 방해하고 불편을 초래할 수 있으므로
- 재시도 로직을 도입하면 실패를 완화할 수 있을 것
  - 하지만 지연 시간과 비용을 늘릴 수 있음
- 까다로운 요청은 사람에게 넘기는 것도 일반적인 방법
  - 특정 문구가 포함된 질의는 상담원에게 전달하는 방식
  - 대화를 언제 사람에게 넘길지 결정하기 위한 특화 모델도 있음

**가드레일 구현**

- 가드레일의 트레이드오프: 신뢰성과 지연 시간
- 지연 시간을 줄이기 위해 스트림 완성 모드를 사용하기도 함
  - 출력 가드레일이 제대로 작동하지 않게 될 수 있음
  - 그래도 사용자가 응답을 보기까지 기다리는 시간이 줄어듦
- 모델이 서드파티 API를 사용한다면 API 제공업체에서 다양한 가드레일을 제공하기 때문에 직접 구현해야 하는 가드레일 수를 줄일 수 있음
- 애플리케이션의 실패 가능 지점이 다양하므로, 가드레일도 다양한 레벨에서 구현 가능
  - 여기서도 안전성과 유연성 사이에서의 트레이드오프 필요

### 3단계: 모델 라우터와 게이트웨이 추가

- 애플리케이션이 더 많은 모델을 다루게 되면, 여러 모델을 서빙하는 데 필요한 라우터 및 게이트웨이가 필요해짐

**라우터**

- 모든 질의에 하나의 모델만 사용하는 대신, 질의 유형별로 각기 다른 솔루션을 채택할 수 있음
- 여러 모델 사용의 장점들
  - 특정 질의의 경우 범용 모델보다 특화 모델이 더 유용할 수 있음
  - 비용 절약 (단순한 질의는 저렴한 모델로)`
- 라우터는 보통 사용자의 의도를 예측하는 **의도 분류기(intent classifier)** 로 구성됨
  - 예측된 의도를 바탕으로 질의를 적절한 솔루션으로 전송
  - 애매한 질의에 대해 더 자세히 물어보도록 하는 데에 도움이 될 수 있음
- **다음 행동 예측기(next-action predictor)**
  - 라우터는 모델의 다음 행동을 결정하는 데 도움을 줄 수 있음
  - 라우터는 모델이 메모리 계층의 어느 부분에서 정보를 가져와야 할지 예측 가능
- 의도 분류기와 다음 행동 예측기는 파운데이션 모델 기반으로 구현 가능
  - 작은 언어 모델을 빠르고 저렴하게 활용
- 다른 모델로 질의를 라우팅할 때는 질의의 컨텍스트를 해당 모델에 맞게 조정해야 할 수도 있음
- 라우팅은 다른 모델과 함께 묶여서 활용될 수 있지만, 검색보다 먼저 라우팅을 하는 경우가 대다수라는 점을 명심할 것
  - 보통 '라우팅 - 검색 - 생성' 순서로 진행
  
**게이트웨이**

- 모델 게이트웨이는 조직이 다양한 모델과 통합되고 안전한 방식으로 상호작용할 수 있게 해주는 중간 계층
- 가장 기본적인 기능: 자체 호스팅 모델과 상용 API 모델을 포함한 다양한 모델에 통합 인터페이스 제공
- 모델 API가 변경되더라도 API에 의존하는 모든 애플리케이션을 업데이트할 필요 없이 게이트웨이만 업데이트하면 됨
- **접근 제어(access control)** 와 **비용 관리(cost management)** 기능
  - 모델 게이트웨이를 단일 접근 지점으로 만들고 여기에만 접근 권한을 부여하게 할 수 있음
  - 어떤 사용자나 애플리케이션이 어떤 모델에 접근 가능한지 명시하는 세분화된 접근 제어 구현 가능
  - 또한 API 호출 사용량을 모니터링하고 제한할 수 있음
- **fallback policy**
  - 속도 제한이나 API 실패를 극복하기 위한 정책
  - 요청을 대체 모델로 보내거나, 잠시 기다린 후 재시도하거나, 또다른 방식 활용 가능
  - 이렇게 함으로써 애플리케이션이 중단 없이 원활히 작동하도록 보장
- 로드 밸런싱, 로깅, 분석 등의 부가 기능들
  - 모든 요청과 응답은 게이트웨이를 거치게 되므로, 부가 기능들을 구현하기에 가장 적합
  - 일부 게이트웨이는 캐싱이나 가드레일 기능을 제공하기도 함
- 쓸만한 게이트웨이들
  - [Portkey-AI Gateway](https://github.com/Portkey-AI/gateway)
  - [MLflow AI Gateway](https://mlflow.org/docs/latest/genai/governance/ai-gateway/)
  - [Truefoundry](https://www.truefoundry.com/docs/ai-gateway/intro-to-llm-gateway)
  - [Kong AI Gateway](https://konghq.com/products/kong-ai-gateway)
  - [Cloudflare AI Gateway](https://developers.cloudflare.com/ai-gateway/)

### 4단계: 캐시로 지연 시간 줄이기

- 이미 KV 캐싱 및 프롬프트 캐싱 등을 다뤘고, 시스템 캐시는 자료가 워낙 방대하기 때문에 핵심만 간단히 다룰 것

**완전 일치 캐싱(exact caching)**

- 정확히 같은 항목이 요청될 때만 캐시된 항목 사용
- 예시 1
  - 사용자가 모델에게 제품 요약 요청
  - 시스템은 정확한 제품 요약이 캐시에 있는지 확인
  - 있으면 요약을 가져오고, 없으면 요약을 캐시에 저장
- 벡터 검색 중복을 피하기 위해, 임베딩 기반 검색에서도 사용됨
  - 질의가 이미 검색 벡터 캐시에 있다면 캐시 결과 반환
  - 없다면 질의에 대한 벡터 검색 수행 후 결과를 캐시에 저장
- 생각의 사슬(CoT)처럼 여러 단계를 포함하거나, 검색, SQL 실행처럼 시간이 오래 걸리는 동작에 특히 효과적
- 인메모리 저장소를 사용해 빠른 검색 기능 구현 가능
  - PostgreSQL, Redis 등을 계층형으로 활용해서 구현할 수도 있음
- 캐시 제거 정책도 중요
  - LRU(Least Recently Used)
  - LFU(Least Frequently Used)
  - FIFO(First In First Out)
- 캐시 TTL은 해당 질의가 호출될 가능성에 따라 달라짐
  - 어떤 질의를 캐시에 저장해야 할지 예측하는 별도의 분류기를 학습시키기도 함

**시맨틱 캐싱(semantic caching)**

- 질의가 캐시 항목과 완전히 일치하지 않더라도 의미적으로 비슷하면 캐시된 항목을 사용
- 캐시 적중률을 높이고 잠재적 비용도 줄일 수 있지만, 모델의 성능을 저하시킬 수 있음
- 시맨틱 캐싱은 두 질의의 유사도를 판단할 수 있는 방법이 확실히 존재할 때에만 작동
- 의미적 유사도 작동 방식 상기 (3장 내용)
  - 질의마다 임베딩 모델을 사용해 임베딩 생성
  - 벡터 검색으로 현재 질의 임베딩과 가장 높은 유사도 점수를 가진 캐시된 임베팅 탐색
  - 만약 유사도 점수가 유사도 임계값보다 높으면 캐시 유효로 판단하고 결과 반환
  - 유사도 점수가 임계값보다 낮으면 현재 질의를 처리하고 결과와 임베딩을 함께 캐시에 저장
- 임베딩 방식은 벡터 DB가 필요
- 시맨틱 캐싱은 구성 요소들이 망가지기 쉬워서 애매한 부분도 있음
  - 제대로 작동하려면 좋은 품질의 임베딩, 안정적인 벡터 검색, 신뢰 가능한 유사도 측정 모두 필요
  - 적절한 유사도 임계값을 설정하는 것도 시행착오를 많이 겪어야 하는 까다로운 부분
  - 벡터 검색은 시간도 오래 걸리고 연산량도 많음
- 그래도 캐시 적중률이 높다면 여전히 가치가 있을 수 있음
  - 다만 효율성, 비용, 성능 위험을 꼼꼼히 검토해야 함

### 5단계: 에이전트 패턴 추가

- 4단계까지는 각 질의가 순차적인 흐름을 따르므로 꽤 단순한 편
- 그러나 실제 애플리케이션 흐름은 루프, 병렬 실행, 조건부 분기 등 복잡성이 높음
- 모델의 쓰기 작업 접근 권한은 특히 더 신중하게 다뤄져야 함

### 모니터링과 관찰 가능성

- 관찰 가능성(observability)은 나중에 덧붙이는 것이 아니라 제품 설계 때부터 핵심에 두어야 함
- 제품이 복잡해질수록 관찰 가능성은 더욱 중요해짐
- 관찰 가능성은 이미 모든 소프트웨어 엔지니어링 분야에서 널리 쓰이고 있으며, 검증된 모범 사례, 상용 및 오픈 소스 솔루션을 갖추고 있음
- 이 책에서는 파운데이션 모델 기반 애플리케이션에서 나타나는 고유한 문제와 기법들에 초점을 맞출 것
- 모니터링 목표 = 평가 목표
  - 위험을 줄이고 기회를 발견하는 것
  - 애플리케이션 실패, 보안 공격, 드리프트 등의 위험
  - 애플리케이션 개선과 비용 절감의 기회를 발견하는 데 도움이 될 수 있음
- DevOps 커뮤니티에서 나온 시스템 관찰 가능성 수준 평가 지표 3가지
  - **평균 탐지 시간(Mean Time To Detection, MTTD)** : 문제 발생 시, 감지에 얼마나 걸리는가?
  - **평균 응답 시간(Mean Time To Response, MTTR)** : 문제 감지 후, 해결에 얼마나 걸리는가?
  - **변경 실패율(Change Failure Rate, CFR)** : 수정 및 롤백이 필요한 실패를 일으키는 변경 및 배포의 비율
- 평가 지표가 모니터링 지표로 자연스럽게 이어져야 함
  - 즉, 평가 단계에서 좋은 성능을 보인 모델이라면 모니터링에서도 좋은 성능을 보여야 함
  - 모니터링 중에 발견된 문제는 평가 파이프라인에 반영되어야 함

**지표**

- 모니터링 하면 지표가 가장 먼저 떠오르지만, 지표 자체는 목적이 아님
- 지표의 목적: 뭔가 잘못됐을 때 알려주고 개선할 기회를 찾는 것
- 따라서 어떤 실패 유형을 잡아내고 싶은지 먼저 생각하고, 이런 실패들을 중심으로 지표를 설계하는 것이 중요
- 추적하기 가장 쉬운 실패 유형 = 형식 실패
  - 눈에 띄기 쉽고 검증도 쉬움
- 개방형 생성의 경우 사실 일관성, 간결성, 창의성, 긍정성 같은 관련 생성 품질 지표 모니터링을 고려해 볼 것
  - 상당수는 AI 평가자를 사용해서 계산 가능
- 안전성의 경우 유해성 관련 지표 추적, 개인 정보 및 민감 정보 탐지 등이 중요
  - 가드레일이 얼마나 자주 작동하는지
  - 시스템이 얼마나 자주 응답을 거부하는지
  - 시스템에 들어오는 이상한 질의도 탐지해야 함
- 모델 품질에 대해 추적 가능한 지표 예시들
  - 사용자가 중간 생성을 중단하는 빈도는 얼마나 되는가?
  - 대화당 평균 턴 수는 얼마인가?
  - 입력당 평균 토큰 수는 얼마인가?
  - 출력당 평균 토큰 수는 얼마인가?
  - 모델의 출력 토큰 분포는 어떠한가?
- 길이 관련 지표는 지연 시간과 비용 추적에 필요
- 애플리케이션 파이프라인의 구성 요소마다 고유 지표가 존재
  - RAG 애플리케이션에서는 검색 품질 평가를 위해 주로 컨텍스트 관련성과 컨텍스트 정확도 사용
  - 벡터 데이터베이스는 데이터 색인화에 필요한 저장 공간의 양과 데이터 쿼리 시간으로 평가
- 지표 간 상관관계를 추적하는 것도 유용
  - DAU, 세션 지속 시간, 구독 수 등 비즈니스 핵심 지표의 상관관계
- 사용자 수가 늘어날수록 시스템이 어떻게 확장되는지 보기 위해 모든 지표를 사용자별로 추적해야 함
- 비용 추적
  - 질의 수, 초당 토큰 수(TPS) 등 입출력 토큰의 양
  - 속도 제한 API가 있다면 TPS를 추적해 할당된 한도 내에서 서비스를 사용하도록 해야 함
- 표본 검사 / 전수 검사
  - 표본 검사: 데이터의 일부를 샘플링해서 문제를 빠르게 찾아내는 방식
  - 전수 검사: 모든 요청을 평가해서 포괄적인 성능 정보를 파악하는 방식
  - 시스템 요구사항 및 가용 자원에 따라 어떤 것을 선택할지가 달라짐
  - 둘을 적절히 조합하면 균형 잡힌 모니터링 전략을 만들 수 있음
- 지표 계산 시 사용자, 릴리즈 버전, 프롬프트/체인 버전, 프롬프트/체인 타입, 시간 등의 기준으로 세분화가 가능한지 확인해야 함

**로그와 트레이스**

- 지표는 보통 집계된 값이며, 이를 통해 시스템이 어떻게 작동하는지 한눈에 파악이 가능해짐
- 하지만 지표만으로는 답할 수 없는 문제들이 여전히 많음
  - 지표가 급증하는 사유 등
- 지표는 속성과 이벤트를 나타내는 수치적 측정값
- 로그는 **append-only** 이벤트 기록
- 운영 환경에서 대략적인 디버깅 양상
  - 지표가 방금 문제가 생겼다고 알려주지만, 정확히 무슨 일이 일어났는지 알려주지 않음
  - 이벤트의 로그를 보고 무슨 일이 일어났는지 알아냄
  - 로그상 에러와 지표를 연관지어서 문제를 올바르게 식별했는지 확인
- 빠른 탐지를 위해 지표는 빠르게 계산되어야 하고, 빠른 대응을 위해 로그는 바로 확인 가능해야 함
- 로깅의 일반적인 원칙: 모든 것을 로깅한다
  - 모델 API 엔드포인트
  - 모델 이름
  - 샘플링 설정(온도, top-p, top-k, 중단 조건 등)
  - 프롬프트 템플릿
  - etc
- 모든 것을 로깅하므로 로그의 양은 매우 빠르게 증가할 수 있음
  - 따라서 자동화된 로그 분석과 로그 이상 탐지를 위한 많은 도구가 AI로 구동됨
  - 모든 로그를 수동으로 처리하는 것은 불가능에 가깝지만, 매일 운영 데이터를 수동으로 살펴보는 과정이 유용함
    - 좋은 응답의 가능성을 높이도록 프롬프트를 수정할 수 있게 됨
    - 나쁜 응답을 잡아내기 위해 평가 파이프라인 업데이트
- 로그는 개별 이벤트들을 따로 기록
- 트레이스는 관련된 이벤트들을 하나로 연결해서 하나의 트랜잭션이나 프로세스의 완전한 타임라인으로 만든 것
- 트레이스는 요청이 다양한 시스템 구성 요소와 서비스를 거쳐 실행되는 경로를 자세히 기록한 것
- 트레이스는 각 단계별 소요 시간과, 가능하다면 비용도 함께 보여줘야 함
- 트레이스를 활용할 때, 이상적으로는 각 질의가 시스템을 거쳐가며 변화하는 과정을 단계별로 추적 가능해야 함
  - 질의 실패 시 어느 단계에서 문제가 발생했는지 정확히 집어낼 수 있도록

**드리프트 감지**

- 시스템 구성 요소가 많을수록 바뀔 수 있는 것도 많아짐
- AI 애플리케이션에서 바뀔 수 있는 요소들
  - **시스템 프롬프트 변경**
    - 기반 템플릿이 업데이트 된 경우
    - 변경 감지는 간단한 로직만으로도 충분
  - **사용자 행동 변화**
    - 시간이 지나면서 사용자들은 기술에 맞춰 행동을 바꿈
    - 사용자들의 수준이 높아지면서, 애플리케이션에서도 더 나은 결과를 얻기 위한 지시를 쓰는 법을 배우게 됨
  - **기반 모델 변경**
    - API로 모델을 사용할 때, 기반 모델이 업데이트 될 수 있음
    - 이러한 변경사항을 탐지하는 것은 사용자의 몫

### AI 파이프라인 오케스트레이션

- AI 애플리케이션은 시간이 지날수록 여러 모델로 구성되고, 많은 DB를 활용하며, 광범위한 도구에 접근하게 되면서 상당히 복잡해짐
- 오케스트레이터는 복잡성 해소를 위해 서로 다른 구성 요소들의 상호작용 방식을 정의하고, 엔드투엔드 파이프라인을 구성
- 오케스트레이터의 2가지 작동 단계
  - **구성 요소 정의(components definition)**
    - 시스템의 구성 요소들을 오케스트레이터에 알려야 함
    - 다양한 모델, 외부 데이터 소스, 시스템이 사용 가능한 도구 등
    - 모델 게이트웨이를 사용한다면 모델을 더 쉽게 추가 가능
  - **체이닝(chaining)**
    - 체이닝은 기본적으로 함수를 조합하는 것
    - 체이닝은 사용자 질의를 받는 순간부터 작업 완료까지 시스템이 수행하는 단계들을 오케스트레이터에게 알려줌
    - 체이닝 단계의 대략적인 예시
      - 원본 질의 처리
      - 처리된 질의를 바탕으로 관련 데이터 검색
      - 원본 질의와 검색된 데이터를 결합해서 모델이 예상하는 형식의 프롬프트 생성
      - 모델이 프롬프트 바탕으로 응답 생성
      - 응답 평가
      - 응답이 좋다고 판단되면 사용자에게 반환하고, 아니라면 질의를 상담원에게 전송
- 오케스트레이터는 구성 요소들 사이에서 데이터를 전달하는 역할 수행
  - 현재 단계의 출력이 다음 단계에서 예상하는 형식인지 확인해 주는 도구를 제공해야 함
  - 이상적으로는 구성 요소 실패나 데이터 불일치 오류 때문에 이런 데이터 흐름이 끊어질 때 사용자에게 알려줘야 함
- 지연 시간 요구사항이 엄격한 경우에는 가능한 한 많은 작업을 병렬로 처리
- AI 오케스트레이션 도구들
  - [Langchain](https://github.com/langchain-ai/langchain)
  - [LlamaIndex](https://github.com/run-llama/llama_index)
  - [Flowise](https://github.com/FlowiseAI/Flowise)
  - [Langflow](https://github.com/langflow-ai/langflow)
  - [Haystack](https://github.com/deepset-ai/haystack)
- 처음 프로젝트를 시작할 때는 오케스트레이션 도구 없이 만들어 보는 것을 추천
  - 외부 도구는 어떤 것이든 복잡성을 더하기 때문
  - 핵심 세부사항에 대한 추상화는 시스템 이해 및 디버깅을 어렵게 할 수 있음
- 오케스트레이터를 평가할 때 명심해야 할 3가지
  - **통합과 확장성**
    - 현재 사용 중이거나 앞으로 도입 예정인 구성 요소들을 지원하는지 평가해야 함
    - 세상에는 수많은 모델, DB, 프레임워크가 존재하므로 오케스트레이터가 모든 것을 지원하는 것은 불가능
    - 그러므로 미지원 구성 요소를 직접 확장하는 것이 얼마나 어려운지도 검토해봐야 함
  - **복잡한 파이프라인 지원**
    - 애플리케이션이 복잡할수록 여러 단계와 조건부 로직을 포함하는 파이프라인을 관리하게 됨
    - 오케스트레이터가 분기, 병렬 처리, 오류 처리 등 고급 기능을 지원하는지 여부를 확인할 것
  - **사용 편의성, 성능, 확장성**
    - 오케스트레이터의 사용자 친화성도 중요
    - 직관적 API, 포괄적 문서, 강력한 커뮤니티 지원 여부 확인
    - 몰래 API를 호출하거나 지연 시간을 유발하는 오케스트레이터는 되도록 피할 것
    - 애플리케이션이 확장되면서 오케스트레이터도 효과적으로 확장될 수 있을지 검증

## 10.2 사용자 피드백

- 일반적인 애플리케이션에서 사용자 피드백의 2가지 핵심 역할
  - 애플리케이션 성능 평가
  - 개발 방향에 정보 제공
- AI 애플리케이션에서는 사용자 피드백이 훨씬 더 중요한 역할
  - 사용자 피드백은 독점 데이터이며, 경쟁 우위의 원천
- 데이터 플라이휠을 만들기 위해 잘 설계된 사용자 피드백 시스템이 꼭 필요
- 사용자 피드백은 곧 사용자 데이터
  - 민감한 데이터를 활용할 때 조심해야 함

### 대화형 피드백 추출

<!-- 이미지 추천: 명시적 피드백 vs 암시적 피드백 예시 다이어그램.
     왼쪽: 명시적 피드백 - 좋아요/싫어요 버튼, 별점, 체크박스 UI 예시.
     오른쪽: 암시적 피드백 - 중간 종료, 재생성 클릭, 오류 교정 메시지 등 사용자 행동 패턴.

- 피드백의 전통적인 2가지 분류
  - **명시적 피드백(explicit feedback)**
    - 좋아요/싫어요, 추천/비추천, 별점 평가 등의 질의에 대한 사용자 피드백
    - 어느 애플리케이션에서나 방식이 비슷함
  - **암시적 피드백(implicit feedback)**
    - 사용자 응답이 아닌 행동에서 추론한 정보
    - 애플리케이션의 특성에 따라 무엇을 암시적 피드백으로 간주할지가 달라짐
- 대화형 AI 애플리케이션은 사용자 피드백을 받기 쉬움
  - 대화에서 추출한 사용자 피드백에 대한 사용 사례
    - **평가**: 애플리케이션을 모니터링할 지표 도출
    - **개발**: 향후 모델 학습이나 개발 방향 안내
    - **개인화**: 각 사용자에게 맞게 애플리케이션을 개인화
- **암시적 대화형 피드백(implicit conversational feedback)**
  - 사용자 메시지 내용과 의사소통 패턴 둘 다에서 추론 가능
  - 일상 대화 속에 피드백이 섞여 있기 때문에 추출이 어려움
  - 꼼꼼한 데이터 분석과 사용자 연구가 필요

**자연어 피드백**

- **조기 종료**
  - 사용자가 응답을 중간에 멈추게 한 경우
  - 혹은 단순히 에이전트를 방치한 경우
  - 대화가 잘 이뤄지고 있지 않을 가능성이 높음
- **오류 교정**
  - 사용자가 후속 질의에서 오류를 바로잡으려고 하는 경우
  - 모델의 응답이 빗나갔을 가능성이 높음
  - 모델의 오해를 바로잡으려는 사용자의 시도가 피드백 데이터
  - 휴리스틱이나 ML 모델을 사용해서 탐지 가능
  - 모델은 이러한 피드백을 받아서 요약을 수정할 수 있어야 함
  - 행동 교정 피드백은 사용자가 에이전트를 더 좋은 행동으로 유도하는 에이전트 활용 사례
  - 이는 세부 사항이 부족하다는 의미일 수도, 모델을 못 믿겠다는 신호일 수도 있음
  - 일부 애플리케이션에서는 사용자가 직접 모델 응답을 편집할 수도 있게 해둠
- **불평**
  - 사용자가 출력 교정을 시도하지 않고 그냥 불평만 하는 경우
  - **대화형 대화 및 검색 피드백(Feedback for Interactive Talk & Search)** 데이터셋에서 나타난 피드백 유형 순위
    - 요구사항을 다시 명확히 설명
    - 봇에 질의에 답하지 않거나, 관련 없는 정보를 주거나, 사용자가 직접 답을 찾아보게 했다고 불평
    - 질의에 답이 될 만한 특정 검색 결과 제시
    - 봇이 검색 결과를 사용해야 한다고 제안
    - 응답이 사실과 다르거나, 검색 결과에 근거하지 않았다고 말함
    - 봇의 응답이 구체적이지 않거나, 정확하지 않거나, 완전하지 않거나, 상세하지 않았다고 말함
    - 봇이 자신의 응답에 확신이 없는 느낌으로 시작한다고 언급
    - 봇 응답의 반복이나 무례함에 대해 불평
  - 봇이 어떤 지점에서 사용자를 만족시키지 못하는지 이해하는 것이 매우 중요
- **감정**
  - 사용자가 불평을 할 때 이유를 설명하거나 하지 않고, 부정적인 감정(좌절, 실망, 조롱 등)을 표현할 때도 있음
  - 봇과의 대화 전반에 걸친 사용자 감정을 분석하면 봇이 어떻게 작동하는지에 대한 통찰력을 얻을 수 있음

**기타 대화형 피드백**

- **재생성**
  - 사용자가 응답 재생성을 선택했다면 첫 번째 응답이 만족스럽지 않았을 가능성이 있음
  - 첫 번째 응답이 괜찮았지만 비교할 다른 옵션을 보고 싶어서일 수도 있음
    - 이미지나 이야기 생성 등 창의적인 요청에서 흔함
  - 구독 기반이 아닌, 사용량 기반 과금일 때 의미가 더 클 수 있음
    - 추가 비용을 지불하면서까지 재생성을 했다는 의미이기 때문에
  - 재생성 후 일부 애플리케이션은 새로운 응답을 이전 응답과 비교해달라고 직접 요청하기도 함
    - 이 데이터는 선호도 파인튜닝에서 다시 사용될 수 있는 데이터
- **대화 관리**
  - 삭제, 이름 변경, 공유, 북마크 등 사용자가 대화를 관리하기 위해 취하는 행동
  - 대화 삭제는 그 대화가 좋지 않았다는 강력한 신호
    - 물론 부끄러운 대화라 지우고 싶은 경우는 제외
  - 대화 이름 변경은 대화 내용과 상관 없이 자동으로 생성된 제목이 별로였음을 시사
- **대화 길이**
  - 대화당 턴 수
  - 좋은 신호인지 나쁜 신호인지 여부는 애플리케이션에 따라 다름
  - AI 친구 같은 느낌이라면 긴 대화는 사용자가 대화를 즐기고 있다는 뜻
  - 고객 지원 챗봇이라면 긴 대화는 사용자 문제 해결에 비효율적이라는 뜻
- **대화 다양성**
  - 대화 길이는 고유 토큰, 주제 개수 등 측정 가능한 대화 다양성과 함께 해석 가능
  - 대화가 길지만 봇이 같은 말을 반복하고 있다면 사용자는 루프에 빠졌을 가능성이 있음

**명시적 피드백과 암시적 피드백 정리**

- 명시적 피드백
  - 해석하기 더 쉬움
  - 사용자에게 추가적인 노력 요구
  - 그렇기 때문에 사용자가 굳이 피드백을 주지 않는 경우도 많음
  - 응답 편향의 문제가 발생할 수 있음
    - 불만족한 사용자들이 불평할 가능성이 더 높을 수 있음
- 암시적 피드백
  - 훨씬 풍부하지만 그만큼 더 노이즈가 많음
  - 따라서 암시적 신호 해석이 어려움
  - 암시적 응답 추출, 해석, 활용은 작지만 성장하는 연구 분야

### 피드백 설계

**피드백을 수집하는 시점**

- 피드백은 사용자 여정 전반에 걸쳐 수집해야 함
- 특히 오류 발생 시 사용자가 언제든지 피드백을 남길 수 있도록 여건을 마련해야 함
- 단, 피드백 수집 옵션이 사용자에게 거슬리지 않아야 함 ⇒ 사용자의 흐름을 방해해선 안 됨
- 사용자 피드백이 유용한 상황들
  - **처음 시작할 때**
    - 사용자를 위한 초기 애플리케이션 동작 보정에 도움이 될 수 있음
    - 얼굴 인식, 음성 인식, 학습 수준 파악 등 초기 보정이 꼭 필요한 경우도 있음
    - 필수로 수집할 게 없다면 가급적 초기 피드백은 선택 사항으로 남겨두는 것이 좋음
  - **문제가 생겼을 때**
    - 모델의 환각, 정당한 요청의 차단, 응답의 심각한 지연 등의 문제에 대해 피드백을 남길 수 있어야 함
    - 혹은 응답에 '싫어요' 반응을 누르거나, 응답 재생성, 모델 변경 등의 선택지를 줄 수 있음
    - 이상적으로는 제품이 실수를 해도 사용자들은 여전히 작업을 완수할 수 있어야 함
    - 사용자가 AI와 협력하면서 기능을 완수할 수 있도록 설계해야 함
  - **모델의 신뢰도가 낮을 때**
    - 모델 입장에서 행동에 대한 확신을 못할 때, 사용자에게 피드백을 요청해서 신뢰도를 높일 수 있음
    - 지연 시간을 지나치게 늘리지 않는 선에서 응답을 2개를 보여주고 선택하게 할 수 있음

**피드백 수집 방법**

- 피드백은 사용자의 워크플로에 자연스럽게 녹아들어야 함
- 사용자는 별다른 수고 없이 쉽게 피드백을 줄 수 있어야 함
- 혹은 쉽게 피드백 요청을 무시할 수도 있어야 함
- 추가로 사용자가 좋은 피드백을 주도록 유도하는 인센티브도 있어야 함
- 좋아요/싫어요 정보만 봐도 제품 분석에 도움이 됨
- 더 깊이 있는 분석을 위해 이전 5-10번의 대화 같은 주변 컨텍스트가 필요
- 하지만 컨텍스트에 개인 식별 정보가 포함된 경우에는 명시적 동의 없이는 수집 불가
- 일부 서비스는 분석 및 제품 개선을 위해 사용자 데이터 접근을 허용하게 하는 조항을 넣기도 함
- 사용자의 이해를 돕기 위해 선택지에 아이콘이나 툴팁을 추가하자
- 사용자 피드백 공개/비공개 여부도 결정해야 함
- 사용자들은 비공개 피드백을 줄 때 더 솔직해지는 경향이 있음
- 하지만 비공개 신호는 **발견 가능성(discoverability)** , **설명 가능성(explainability)** 을 낮출 수도 있음

### 피드백의 한계

**편향**

- **관대함 편향**
  - 사람들이 실제보다 더 긍정적으로 평가하는 경향
  - 갈등을 피하고 싶거나, 친절해야 한다고 느끼거나, 단순히 그게 쉽기 때문에 발생
  - 그냥 빨리 끝내기 위해 대강 긍정적인 응답을 하는 경우도 있음
  - 따라서 사용자 피드백을 위해 사용자가 추가 작업을 하지 않도록 만드는 것이 중요
  - 점수를 부여하는 대신, 구체적인 느낌들을 선택지로 줘서 편향을 줄여줄 수 있을 것
- **무작위성**
  - 사용자들은 종종 신중하게 생각할 동기가 부족해서 아무렇게나 피드백을 줌
  - 읽는 시간이 아깝고 귀찮아서 무작위로 선택하게 될 수 있음
- **위치 편향**
  - 선택지가 사용자에게 어떤 위치로 제시되느냐가 선택지에 대한 인식에 영향을 줌
  - 사용자들은 일반적으로 첫 번째 제안을 클릭할 가능성이 높음
  - 제안의 위치를 무작위로 바꾸거나 위치에 따른 제안의 실제 성공률을 계산하는 모델을 활용할 수 있을 것
- **선호도 편향**
  - 길이가 더 긴 응답이 정확하다고 판단될 수 있음
  - 최근성 편향에 따라, 마지막에 본 응답을 선호하는 경향이 있음

**퇴화 피드백 루프**

- 사용자 피드백은 사용자에게 보여준 것에 대한 피드백만 얻을 수 있기 때문에 기본적으로 불완전
- 사용자 피드백이 모델의 동작을 수정하는 시스템에서는 **퇴화 피드백 루프**가 발생할 수 있음
- 퇴화 피드백 루프: 예측 자체가 피드백에 영향을 주고, 이 피드백이 다시 모델의 다음 버전에 영향을 주면서 초기 편향이 점점 심해지는 증상
- '노출 편향', '인기 편향', '필터 버블' 등
- 제품의 초점과 사용자층을 바꿔버릴 수도 있음
  - 초기에 고양이 사진이 좋은 평가를 받아버리면, 나중에 애플리케이션이 고양이 천국이 될 수도 있음

⇒ 사용자 피드백은 중요하지만, 무분별하게 사용하면 편향을 만들고 제품을 망칠 수도 있으므로, 피드백의 한계 및 잠재력을 제대로 이해해야 함
